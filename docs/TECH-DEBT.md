# Tech Debt

A ledger of code-quality / robustness items that are not features (those live in
[`TODO.md`](../TODO.md)): debt to fix deliberately, and debt we **chose** to live
with and why.

Two sections:

- **Open — to address** — known debt we intend to pay down when it's convenient
  (usually folded into the next PR that touches the area).
- **Accepted — deliberately not fixing (for now)** — debt we've looked at and
  consciously decided to leave, with the rationale. Revisit only if the stated
  assumption breaks.

A paid-down item is deleted from this file. Code comments cite some ids that are
not listed here (for example TD-2, TD-6, TD-15a, TD-15b, TD-16, TD-17):
an id not listed below is closed, and git history holds its entry.

## Open — to address

| # | Area | Item | Why it matters | Size |
|---|---|---|---|---|
| TD-7 | Mobile / scale | **Full catalog-snapshot endpoint is ~20 s for 1,209 books** (measured via App Insights on Basic-tier SQL). `GetCatalogSnapshot` projects nested works/editions/contributors/isbns — a heavy shape that climbs with the catalogue. The mobile app forces a full snapshot on the first refresh after any server-version bump, so a slow snapshot is exactly when the transient transport failures (see TD-A5) bite. | Toward the 3000+ target the snapshot time grows and the failure window widens. Best handled in a `/scale-audit` pass (gzip the response, `AsSplitQuery`, projection trimming) — distinct surface from the Library-page load. | M |
| TD-8 | Mobile | **`ThemeColors.Get` resolves design tokens by magic string** (`"BrassTextL"`, `"TextMutedD"`, …) — a typo'd or renamed key compiles cleanly and throws `KeyNotFoundException` at page-render time (`OnAppearing`), crashing the tab rather than showing a wrong colour. | The typo surface widens as `Colors.xaml` grows (27 light/dark token pairs today). A generated/typed token class (or `nameof`-backed constants validated against the dictionary) would move the failure from a runtime page-crash to a build error. Low risk today (keys are covered as pages adopt them); revisit if a typo bites. | S |
| TD-9 | Mobile | **The Wishlist tab re-queries the cache and re-fires a cover fetch per row on every tab visit.** `AppShell` keeps one `WishlistPage` instance for the app lifetime, so each return to the tab rebuilds all rows and re-issues N best-effort cover HTTP fetches (`WishlistPage.LoadCoverAsync`). Reload-on-appear is *correct* (it's what keeps Gaps fresh) — the waste is the un-deduped cover refetch. | Visible flicker + wasted bandwidth that scales with wishlist size on rapid tab-switching. Fix is cover-fetch dedup/caching (mirror the Book-cover disk cache, or skip refetch when the row's CoverUrl is unchanged), not a load guard. Low priority — wishlists are small. | S |
| TD-12 | Mobile | **The Find tab's sync chip (`SyncChipLabel` in `FindPage`) shows a healthy `⟳ {age}` even when the last sync failed or never ran.** It reads `Meta.SyncedAt` whenever online, regardless of success; combined with `AppShell`'s silent launch-sync `catch {}`, a failed/expired launch sync (or signed-out-but-online) shows a normal-looking age with no "stale / sign in / sync failed" cue. | The user trusts a stale catalogue as current. Real fix pairs with auth-expiry handling in the online-layer arc (#54): model a sync-failed / never-synced (and ideally `IsSyncing`) state and surface it on the chip. Low risk today (sole user, usually a fresh sync); revisit with #54. | S |
| TD-13 | Mobile | **The non-disk-cached cover fetch is copy-pasted across two Bookshelf pages** (`ResultPage.LoadEditionCoverAsync` ≈ `WishlistPage.LoadCoverAsync`). The pages' pure presentation helpers live in `BookTracker.Mobile.Cache/Presentation/` with tests; the cover fetch is the one shared piece written twice. | A change to cover-fetch behaviour must be hand-applied in two places and will drift. Extract a `Covers.LoadFromUrlAsync`. Low risk; fold into the next Mobile PR touching these pages. | S |
| TD-14 | Mobile | **Two altitude items.** (a) The ambient sync chip (live online/age, refreshed on `SyncService.StateChanged`) lives only on the **Find** tab; Wishlist + Gaps use a static "Sync" `ToolbarItem` with no offline/age signal — the offline indicator is missing on 2 of 3 tabs. (b) Inline-camera teardown relies on `OnDisappearing` firing on a tab switch, which is version-dependent under Shell. | (a) Sync state should be one reusable affordance (or a Shell-level chip) bound once, not a per-page reimplementation that drifts. (b) If `OnDisappearing` doesn't fire on a tab switch the camera stays live in the background (battery/privacy) — **needs an on-device check**; if it leaks, hook `Shell` navigation instead of the page lifecycle. | S |

## Accepted — deliberately not fixing (for now)

| # | Area | Item | Decision & rationale |
|---|---|---|---|
| TD-A1 | Library | **Author group drill keys on `group.Label` (canonical name), not the canonical id** — unlike Genre, which keys on `group.Key`. The theoretical `"(unknown)"` label fallback would drill to an empty list. | **Accept.** `Author.Name` is unique (enforced) and `CanonicalAuthorId` is an FK, so the `"(unknown)"` fallback is practically unreachable; name-keying is also *consistent* with the existing name-based author filter shown in the Author autocomplete. Drilling by id would require a new author-id flat filter for no real gain. Revisit only if author-name uniqueness is ever relaxed. |
| TD-A2 | Library | **An unsubmitted search term is committed to the URL by the next non-search filter edit.** Typing in the search box (which waits for Enter) then changing, e.g., Status serialises the typed-but-not-submitted term too. | **Accept.** The search box visibly shows the term — committing what the user can see when they touch another filter is reasonable. Revisit if it surfaces as confusing in dogfooding. |
| TD-A5 | Mobile | **No auto-retry on the catalog refresh** — a post-deploy full-snapshot refresh can fail with a transient transport error (`HttpRequestException`) and succeed on a manual re-tap (server side is clean: ~20 s, no exceptions; the request never completes a round-trip, self-heals on retry). | **Accept — manual re-tap, by Drew's call.** Backoff retry wrapped around a call that can hang ~100 s would freeze the app for minutes with no escape, forcing a cancel button to paper over the retry. Manual re-tap keeps the user in control, and the failure window is rare (only the first refresh after a server-version bump forces a full snapshot; routine refreshes are fast deltas). If it recurs, capture the logcat inner exception (`reset` / `premature` / `Timeout`) to pin the mechanism before reconsidering. |
| TD-A4 | Library | **A `?group=Collection` bookmark/shared link silently degrades to the Author grouping** (there is no Series grouping mode). `Enum.TryParse` fails on the unknown token and falls back to the Author default; the stale `group=Collection` token is also left in the URL (the page only rewrites the query on a `None`-grouping page clamp). | **Accept.** Sole-user app, and the fallback can't recover *which* series was being viewed (the query carries no series id), so any remap would be a guess. Landing on the Author default is a safe, non-crashing degradation; the stale token renders fine and only matters if re-shared. Regression-guarded by `ApplyQueryParameters_FallsBackToDefaultsForAbsentOrJunk`. Revisit only if a real shared-link complaint surfaces. |
| TD-15 | Application | **Residual check-then-insert race in find-or-create on lookup tables.** The interactive single-add pickers resolve authors, publishers and series eagerly at the commit gesture (`CreateAuthor` / `CreatePublisher` / `EnsureSeries`, idempotent find-or-create → id) and the Book/Edition save attaches by id, so the contended save does not own the insert there. The **Bulk Add** grid and system paths (the `MarkWishlistItemBought` follow-up tag) still find-or-create at save time through the `*Resolver` owners and keep the plain check-then-insert race; code comments cite this id. | **Accept.** Near-impossible for a single-user app, and every lookup type has one resolver owner, so a unique-index-catch + re-query upgrade lands in one place if the app ever takes concurrent writers. The aggregate save keeps `*Resolver.ResolveAsync` as a net for ISBN-prefill names that bypass the pickers. |
| TD-A3 | Library | **Author-group drill does not cluster books series-then-standalone.** Drilling an Author group lands on the flat list sorted newest-first (DateAdded), not series-having members first (by series name, then SeriesOrder) with standalones tailing alphabetically. | **Accept for now.** Series browsing sorts by reading order (SeriesOrder). If author-drill clustering is wanted, add it by putting the sort into `LoadBooksAsync` when `SelectedAuthor` is set — but that's a feature decision, not debt. |
| TD-19 | Web / covers | **The SkiaSharp cover pipeline drops EXIF orientation.** `SKBitmap.Decode` ignores the JPEG EXIF orientation tag and `CoverImageProcessor` re-encodes from raw pixels (no tag carried forward), so a cover *uploaded straight from a phone camera* with a non-default orientation could render rotated 90/180°. (The image still decodes, so it is stored; the problem is visual only, not a refusal.) | **Accept.** The dominant cover source is upstream providers (Open Library / Google / Trove) — already-baked thumbnails with no EXIF orientation, so the common path is unaffected; only the manual phone-upload edge is exposed. The mobile cover cache (`CatalogCache.ResizeToJpeg`) decodes the same way and feeds off the same upstream snapshot, so it's consistent. **Fix if a sideways cover actually appears:** read `SKCodec.EncodedOrigin` and apply the transform before encode. |
| TD-18 | Application / read-models | **"Lead author = first Author-role contributor by `Order`" is duplicated across a dozen projection sites**, all in `BookTracker.Application` — among them `GetBookDetail`, `GetAuthorDetail`, `GetLibraryBooks`, `SearchWorks`, `GetSeriesDetail`, `SearchBooksForSeries`, `FindEditionByIsbn`, `GetCatalogSnapshot`, `GetWorkForEdit` and `GetDuplicateReport` — each encoding `WorkAuthors.Where(Role == Author).OrderBy(Order)…` independently (some take `.First()` for the lead deep-link/by-line, some `.Select(Name)` for the full ordered author list). This list is indicative, not exhaustive — the grep below is the source of truth. | **Accept.** No live defect — every site picks the same lead author today; the risk is drift-only. A single shared selector **can't be inlined into the SQL-projection sites** (read handlers) without LinqKit expression-splicing — EF Core won't translate a custom method/expression call inside a projection, and we've deliberately avoided that dependency (à la no-MediatR). A plain C# helper would serve only the sites that work over already-materialised rows while the SQL copies stay duplicated; forcing the rest in-memory to share it would give up the read handlers' SQL projections. Not worth a new dependency to prevent a divergence that hasn't happened in a single-user app. **Revisit if** the lead-author rule itself changes (a new pseudo-role to exclude, a different tie-break): grep the filter predicate `Role == AuthorRole.Author` (filter-only on purpose — the read handlers wrap `.Where(...)` and `.OrderBy(...)` across separate lines, so a single-line `).OrderBy(` pattern misses `GetBookDetail`/`GetAuthorDetail`/`GetLibraryBooks`; the predicate over-matches a few non-pick sites like `AuthorRollups`/`WorkAuthorshipFormatter`, which is the safe direction) to find every copy and change them together. |
